## `docs/handbook/debugging.md`

# Debugging Methodology

*Current as of commit `<hash>`, <date>.*

This document describes how to find bugs in the Prism compiler and
VM. It is written for a maintainer who has a failing test, a
crash, or a wrong result and wants to locate the cause.

The material is organized as: the general method, the tools, then
worked examples from real bugs.

---

## §1 — The general method

Five steps. The order matters.

1. **Reproduce.** Reduce the failing case to the smallest program
   that still fails. A five-line program is easier to reason about
   than a hundred-line one. The test suite's `test_run` helper
   takes a source string; a new test file is often the fastest
   reproduction.

2. **Localize.** Determine which stage is wrong: lexer, parser,
   sema, codegen, or VM. The error message usually names a stage;
   if not, add temporary `fprintf` at stage boundaries.

3. **Read the state.** At the point of failure, what are the
   relevant values? Add prints, or inspect in a debugger.

4. **Compare to invariant.** Either an invariant from
   `arch/invariants.md` is violated, or a fact about the source's
   meaning is not reflected in the state.

5. **Fix at the establishment point.** The failure is at the point
   of *use*; the bug is at the point of *establishment*. Trace
   backward.

The most valuable skill is reading state for structure. A
backtrace with two `analyze_stmt` frames nested tells you a
reentrant call happened. A stack depth that is one higher than
expected at a `POP` tells you an expression left an extra value.
The shape of the state points at the bug.

## §2 — Tools

### §2.1 The disassembly

`manu --quiet=false run <file>` prints a full listing of the
chunk to stdout. Use it whenever a program misbehaves at
runtime. The listing shows:

- Every instruction with its offset.
- The line and column of the source it came from.
- Operand values with their meaning (pool indices expanded,
  descriptors rendered).

Cross-reference an instruction's pc against the source's line
numbers. A wrong instruction at a known line points at a
specific codegen case.

The listing is generated by `disassemble` in `disasm.c`. It does
not stop at `HALT`.

### §2.2 The trace

`manu --trace run <file>` (or `-t`) enables the VM's
per-instruction trace to stderr. Each line shows the pc, opcode
number, and stack depth.

The trace is verbose. Use it when the failure is a wrong control
flow or a stack imbalance; the pc sequence shows exactly where
control went.

### §2.3 `vm.error_pc`, `vm.error_func_idx`

After a runtime error, the VM has:

- `vm.error` — the message (256 bytes).
- `vm.error_pc` — the pc of the failing instruction.
- `vm.error_func_idx` — the index of the failing function.
- `vm.call_stack[]` — the frame chain.

The driver's `render_runtime_error` uses these to print a source
excerpt and a call trace. A test can read them directly.

### §2.4 `validate_bytecode`

`main.c` runs `validate_bytecode` between codegen and execution.
A return of -1 means a structural error: an invalid opcode, a
truncated instruction, a jump out of range, an invalid operand.

The validator is the boundary between codegen and the VM. A
program that passes the validator will not fail on a malformed
instruction; if it fails at runtime, the failure is a bug in the
bytecode's *semantics*, not its *structure*.

### §2.5 gdb

Useful for crashes and for infinite loops. Break on
`vm_run`, step, or set a breakpoint in a specific opcode's case.
The source is small; a compile with `-g` and no optimization
(`make debug` or manual `-O0 -g`) gives reasonable backtraces.

### §2.6 AddressSanitizer

`make debug` builds with `-fsanitize=address -fno-omit-frame-pointer`.
Run the test suite under ASAN to catch use-after-free, double-free,
and buffer overruns. The recent RC work was validated this way.

ASAN's reports name the allocation site, the free site, and the
use site. For a heap corruption bug in the RC path, this is the
fastest route to the cause.

### §2.7 Temporary `fprintf`

The most flexible tool. For state corruption bugs, add prints
at candidate points and rebuild. The compiler is one process;
a rebuild is a few seconds.

Guidance: print the *shape* of the state, not just the value.
For a bug in scope handling, print `scope_depth`, `local_count`,
and `rc_scope_count` together. For a bug in slot assignment,
print the slot being read and the frame's extent. The pattern
across prints is usually the bug.

### §2.8 The test suite's helpers

`test_value`, `test_output`, `assert_error`, and
`assert_any_error` in `tests/test.c` give strict assertions. A
test written with `test_value` fails if compilation failed,
rather than silently returning 0.

`test_run` returns 0 on runtime error (after printing the
message). This is deliberate; see §4.6.

## §3 — Where bugs live

By subsystem, from most to least likely:

**Codegen.** The largest and most intricate pass. Bugs here
produce wrong bytecode that passes the validator. The RC-scope
tracking, the field-offset computations, and the register/stack
discipline are the fragile parts.

**Sema.** The second-largest. Bugs here produce wrong
annotations that codegen then acts on. The literal-adaptation
path, the RC-managed wrapping, and the local-slot assignment
are the fragile parts.

**VM.** Bugs here produce wrong execution on valid bytecode.
The parameterized opcodes (descriptor dispatch), the RC deep
drop, and the FFI path are the fragile parts.

**Parser.** Bugs here produce wrong ASTs that sema accepts.
The precedence chain, the generic disambiguation, and the
`restrict_struct_lit` flag are the fragile parts.

**Lexer.** Bugs here are rare and usually obvious (a token
misclassified).

**Foundation.** Bugs here (`source_map.c`, `common.c`,
`diagnostic.c`) affect everything and are usually discovered
early.

## §4 — Worked examples

Seven bugs from the recent work stream. Each is presented as:
symptom, tool, reading, source of truth, fix.

### §4.1 The selector bug: `AST_VARIANT_CTOR` used `rd1`

**Symptom.** Every non-generic enum payload constructor
(`Shape.Circle(7)`, `Color.Red(5)`) failed with `unknown type or
module 'Shape'`. Zero-payload variants (`Color.Red`) worked.

**Tool.** Direct source reading. The tests for
`t_enum.c` split cleanly by payload presence; a five-line
reproduction (`type Shape = enum { Circle(i64) }` plus a single
constructor call) isolated the failure.

**Reading.** The `AST_VARIANT_CTOR` case in `sema.c` had two
`ResolvedDecl` variables in scope: `rd` (assigned by
`resolve_name`) and `rd1` (initialized to `rd_none()` and never
reassigned). The enum-construction branch used `rd1`:

```c
ResolvedDecl rd1 = { RD_NONE, -1, NULL };
...
td = resolved_tdef(sc, rd1);   // always NULL
```

`resolved_tdef` on `rd_none()` returns NULL. The subsequent
"unknown type or module" diagnostic was the only path.

**Source of truth.** The type resolution path itself. The zero-
payload case took the `AST_FIELD` path, which uses its own
correct lookup. That's why the split was by payload presence.

**Fix.** One-character: `rd1` → `rd`.

**What to remember.** A variable named `rd1` next to `rd` is a
red flag. Whenever two similar locals appear in the same
function, check that both are used by their intended consumers.
The compiler's diagnostic ("unknown type or module") named the
*effect*; the *cause* was a two-variable naming bug.

### §4.2 The operand-read bug: `OP_DUP2` read `sp-2` twice

**Symptom.** `arr[i] += n` produced garbage. No test exercised
it; the bug was discovered while reading the VM source.

**Tool.** Direct source reading of `vm_run`'s `OP_DUP2` case.

**Reading.**

```c
case OP_DUP2:
    if (vm->sp < 2) RT_ERR("dup2 on shallow stack%s", "");
    U64 a = vm->data_stack[vm->sp - 2];   // pushes a
    U64 b = vm->data_stack[vm->sp - 2];   // BUG
    PUSH(a);
    PUSH(b);
    break;
```

`DUP2` should duplicate the top two slots (`[x, y]` → `[x, y, x,
y]`). Reading `sp-2` twice produces `[x, y, x, x]`, which is the
wrong shape for the caller.

`DUP2`'s only caller is `codegen.c`'s `AST_ASSIGN_OP` for
`AST_INDEX`. The subsequent `OP_INDEX_LOAD` was reading
`arr[arr[i]]` instead of `arr[i]`.

**Source of truth.** The stack invariant documented in
`arch/runtime.md`. The opcode's intended effect is to duplicate
two adjacent slots; the code duplicated one twice.

**Fix.** Two-character: `sp-2` → `sp-1` for the second read.

**What to remember.** Copy-paste errors in stack operations are
subtle because they produce a stack of the right *size* but the
wrong *contents*. A unit test that exercises the opcode directly
(as `t_rc.c`'s or `t_array.c`'s would if written) catches this;
the lack of such a test is why it survived.

### §4.3 The duplicate-evaluation bug: `AST_ASSIGN_OP` for `AST_FIELD`

**Symptom.** Compound assignment to a struct field with an RC
value (`s.count += "x"` where `count` is `string`) would
evaluate the RHS twice and drop the wrong reference. Not
observed in the test suite; found while auditing codegen.

**Tool.** Direct source reading of `cg_stmt`'s `AST_ASSIGN_OP`
case.

**Reading.** The `AST_FIELD` branch had:

```c
if (rc) {
    emit(cg, OP_STORE_LOCAL); emit(cg, (U64)tmp);   // save old
}
cg_expr(cg, val);                       // evaluate new (1)
if (rc) {
    emit(cg, OP_STORE_LOCAL); emit(cg, (U64)tmp);   // OVERWRITE tmp
    emit(cg, OP_LOAD_LOCAL); emit(cg, (U64)tmp);
}
cg_expr(cg, val);                       // evaluate new (2)
...
```

Three problems: `cg_expr(val)` ran twice, the `STORE_LOCAL tmp`
overwrote the saved old value, and the eventual `RC_DEC` dropped
the *new* value (which the code had just stored).

**Source of truth.** The `AST_VAR` case in the same switch.
Comparing the two branches showed the intended pattern was:
save old once, load old once, evaluate RHS once, binary, drop
old, store.

**Fix.** Restructured to match the `AST_VAR` case.

**What to remember.** When a switch has parallel cases for
similar shapes, compare them. Divergence in a case that should
parallel another is a strong bug signal.

### §4.4 The duplicate-wrap bug: `AST_LET` called `coerce_to_target` twice

**Symptom.** No visible failure; the bug was found while reading
sema's `AST_LET` case. In principle, a widening that needed a
runtime conversion (`let x: f64 = some_i32;`) would emit a
doubled `OP_CONVERT`.

**Tool.** Direct source reading.

**Reading.** The `AST_LET` case had:

```c
if (init->type) {
    coerce_to_target(&n->as.let.init, at, it, init->span, bag);
}
...
if (at) {
    if (it) {
        coerce_to_target(&n->as.let.init, at, it, init->span, bag);
    }
    bt = at;
}
```

The first call was redundant; it wrapped the initializer in an
`AST_CAST` when a conversion was needed. The second call wrapped
the cast in another cast. Codegen emitted two `OP_CONVERT`s;
the inner one read f64 bits as if they were i32.

**Source of truth.** The `AST_VAR` and `AST_INDEX` cases in
`analyze_stmt`'s `AST_ASSIGN` handler, which call
`coerce_to_target` exactly once.

**Fix.** Deleted the first call.

**What to remember.** Widening is a code-mutation operation
(it inserts an `AST_CAST`). Calling it twice is idempotent only
when no cast is needed. Annotated `let`s with integer-to-float
widening were affected; the test suite did not exercise this
specific combination.

### §4.5 The codegen/type-system mismatch: unit-variant RC allocation

**Symptom.** `Option.None` in an FFI context produced heap
corruption on Windows. The test suite crashed at
`ffi.option_ptr_arg`. Under ASAN on Linux, a "wild pointer" free
report.

**Tool.** ASAN's report. The free was on an address inside the
arena; the allocation was a `malloc` expected from the RC heap.
The mismatch named the shape of the bug.

**Reading.** `cg_expr`'s `AST_FIELD` case for `unit_tag >= 0`:

```c
if (n->as.field.unit_tag >= 0) {
    set_span(cg, n);
    emit(cg, OP_PUSH); emit(cg, (U64)n->as.field.unit_tag);
    emit(cg, OP_NEW_ENUM); emit(cg, 0);   // always arena
}
```

The value's sema type was `rc<Option<...>>` — RC-managed. The
scope-exit drop emitted `OP_RC_DEC`, which treated the value as
an RC payload and freed the *arena* pointer minus 8.

The correct behavior: use `OP_NEW_RC_ENUM` for RC-managed enums.

**Source of truth.** Every other enum construction site
(`AST_VARIANT_CTOR`, `AST_ALLOC_RC` wrapping a variant) already
selected the opcode by `tdef->is_rc_managed`. This site did not.

**Fix.** Compute `rc_managed = (n->type && n->type->kind ==
TY_RC)`, select `OP_NEW_RC_ENUM` or `OP_NEW_ENUM` accordingly.

**What to remember.** Every allocation site must select the
allocator by the value's tier. The invariant "a value whose sema
type is `rc<T>` is allocated by an `OP_NEW_RC_*` opcode" is
by-convention; it's the check to run against every new allocation
site.

### §4.6 The harness bug: `test_run` read `vm_top` after failure

**Symptom.** A test expected 2 and got 42 — the exact value of
the last argument passed to a failing FFI call. The test claimed
to test `len`, but the FFI call had failed, so `len` was never
reached.

**Tool.** Reading the failing test's actual output and the
`test_run` source.

**Reading.** `test_run`:

```c
int rc = vm_run(&vm);
result = (long long)vm_top(&vm);   // unconditional read
```

`vm_top` returns `data_stack[sp-1]`. After a runtime error, the
stack is in an undefined state; for an FFI call that failed
during argument popping, the stack still held the last argument
(42). The test framework reported that value as the program's
result.

**Source of truth.** The `vm_run` return code. It is 1 on error;
the harness should not read the stack after a failure.

**Fix.**

```c
int rc = vm_run(&vm);
if (rc != 0) {
    fprintf(stderr, "  [test] runtime error: %s\n", vm.error);
    result = 0;
} else {
    result = (long long)vm_top(&vm);
}
```

**What to remember.** A test harness that reads state after a
failure reports garbage as the result. The failure mode is
insidious: the test "fails" with a value that looks plausible
(42 is a reasonable-looking wrong answer), and the diagnostic
that would explain it is buried. Any harness that runs
fallible operations must check the failure code first.

### §4.7 The leak found by a targeted test: `for..in` body RC locals

**Symptom.** No visible failure; the bug was found while reading
`codegen.c` after the RC-scope tracking was added to
`AST_BLOCK`, `AST_FOR_RANGE`, and `AST_MATCH`. `AST_FOR_IN` had
been missed.

**Tool.** Direct source reading, comparing `AST_FOR_IN` against
the other scope-introducing constructs.

**Reading.** `AST_FOR_IN` emitted two `OP_ENTER_SCOPE`s (loop
scope for `arr`/`len`/`idx`, body scope for the loop variable)
but never called `cg_push_rc_scope`. RC locals declared in the
body were registered in the *enclosing* scope's `RcScope`.
At enclosing-scope exit, the drop landed on a slot that had
been reused by a later local; silent corruption.

**Source of truth.** The parallel invariant
`cg->rc_scope_count == cg->scope_depth`. `AST_FOR_IN` was the
only scope-introducing construct that did not maintain it.

**Fix.** Added `cg_push_rc_scope` after each `ENTER_SCOPE` and
`cg_emit_scope_drops` + decrement before each `EXIT_SCOPE`. Also
registered the iterable as an RC local when its type is `TY_RC`.

**Verification.** The `for_in_body_rc` test in `t_memory.c`
exercises a body-scoped RC local; it passes after the fix.

**What to remember.** When a new invariant is introduced
(RC-scope parallelism), audit every existing site that should
maintain it. The invariant's site list is in the doc
(`arch/files/17-codegen.md` §10); a new site added without the
corresponding push/pop is the bug to watch for.

## §5 — What to do when a bug is found

Beyond fixing it:

1. **Add a regression test.** The failing program, minimally
   reduced, becomes a test case. The test file depends on the
   bug's shape: a language-level bug goes in the language file
   (`t_types.c`, `t_aggregate.c`, etc.); a compiler-internal bug
   may need a lower-level test (a test that reads
   `chunk->code` directly, as `t_runtime.c` does).

2. **Check for siblings.** A bug of a given shape often has
   parallel sites. `OP_DUP2`'s operand read suggests checking
   `OP_DUP`'s; `AST_ASSIGN_OP` for `AST_FIELD` suggests checking
   the `AST_VAR`, `AST_DEREF`, and `AST_INDEX` branches.

3. **Update the invariant list.** If the bug revealed an
   invariant that was not previously documented, add it to
   `arch/invariants.md`. If it was documented but not enforced
   structurally, consider whether a structural fix is worth the
   refactor (the RC-scope bundling suggestion, for example).

4. **Record it in the changelog.** A one-line entry in
   `handbook/changelog.md` with the date, the symptom, and the
   fix. This is the only document that records the bug's
   history; a future reader finding the commit message alone
   may not understand the context.

5. **Update the limitation if it applies.** If the bug is a
   manifestation of a known limitation, update that entry. If
   it's a new class of bug, add a limitation.

## §6 — Debugging the FFI

The FFI path crosses into C code the compiler does not own.
Debugging is different.

**Symbol resolution failures.** `ffi_error()` returns the last
`dlerror` message. On Windows, `GetProcAddress` failures are
silent (no equivalent to `dlerror`); the fallback tries
`_<symbol>`. Check the target library's exports with `nm -D`
(Unix) or `dumpbin /exports` (Windows).

**Crashes in the C function.** Run under gdb with the shared
library loaded. A crash inside libffi's `ffi_call` usually
indicates a signature mismatch: a wrong `FFIType` in the
`arg_types[]` array, or a wrong return type. Check the extern
declaration against the C header.

**Wrong results.** `ffi_errno()` returns the `errno` captured
after the call. Some C functions return a sentinel and set
`errno`; a wrong result with a nonzero errno names the failure.

**Option<*T> marshalling.** The unwrap/wrap logic reads the enum
tag and payload directly. A wrong result suggests the enum's
runtime layout does not match the FFI's expectation (tag at
offset 0, payload at offset 8). This is the case for the prelude
`Option`; a user-defined enum with a different layout would
misbehave.

**The `ffi_resolve` failure path.** `ffi_resolve` returns `int`
and propagates errors via `RT_ERR`. If it returns non-zero, the
call site's `ffi_call_dispatch` aborts before `ffi_call`. A
crash inside `ffi_call` therefore means the resolve succeeded
but the cif is wrong; check the `arg_types[]` and the return
type.
